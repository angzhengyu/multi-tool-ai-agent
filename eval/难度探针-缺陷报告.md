## 缺陷 1【★★★ 严重】`run_python` 里相对路径必然失败，把模型困死

**位置**：`tools.py` → `run_python()`，`subprocess.run(..., cwd=str(SANDBOX_DIR))`

**现象**：Agent 写 `pd.read_csv("data/hard/orders_dirty.csv")` → `FileNotFoundError`。
因为子进程的工作目录是 `sandbox/`，而**项目里所有路径约定都是相对项目根目录**的。

**证据**（H03 轨迹）：
```
3. run_python  args={"code": "import pandas as pd\ndf = pd.read_csv(\"data/hard/orders_dirty.csv\")..."}
   -> Traceback ... FileNotFoundError
4. list_files  args={"dir_path": "."}      → 列出项目根（模型想确认文件在不在）
5. list_files  args={"dir_path": "data/hard"}  → orders_dirty.csv, products.csv   （文件确实在）
   最终回答: "The file exists. The issue is the working directory. Let me use an absolute path."
```

H07 里模型甚至打印出了根因：
```
6. run_python -> cwd: D:\AI-Career\05-projects\multi-tool-ai-agent\sandbox
                 path exists (rel): False
                 path exists (abs): False
```

**为什么它救不回来**：`MAX_STEPS = 5` 已经用满（全程 `rounds=6`），
模型虽然诊断对了原因，但**没有下一轮**去用 `DATA_DIR` 绝对路径重试。

**影响面**：需要清洗文本列（`to_numeric`）、去重、跨文件 join 的任务**全部**走这条路 → **0/5**。

**根因**：`run_python` 的 docstring 里写了"可以用 DATA_DIR"，但
**工具描述（`TOOLS_SCHEMA` 里的 description）完全没提这件事**，模型看不到。

**修复建议（两种，按安全取舍）**：
1. **零安全影响（推荐先做）**：在 `TOOLS_SCHEMA` 的 `run_python.description` 里明确写
   「读文件必须用 `DATA_DIR` 拼绝对路径（代码在 `sandbox/` 下执行，相对路径 `data/xxx` 会找不到）」；
   同时在 `_guard` 之外再加一条友好提示：检测到代码里出现 `"data/` 这类相对路径就回一句提醒。
2. **更彻底但改变安全姿态**：把 `cwd` 改成项目根 `BASE_DIR`。
   这样相对路径直接可用，但**被执行的代码就能往项目根目录写文件**（现在只能写进 `sandbox/`）——
   属于放宽隔离，**需要你确认后再动**。

### ✅ 已实施：方案 A（只改描述 + 加失败提示，沙箱一个字节没放宽）

**改动点 1 — 工具描述**（`main.py` 的 `run_python.description`）：

- 明确写出：代码在 `sandbox/` 下执行，**相对路径 `data/xxx.csv` 一定失败**；
- 给出正确写法：`pd.read_csv(DATA_DIR + '/xxx.csv')`；
- 说明 `DATA_DIR` 是预置变量，指向本项目的 `data/` 目录。

**改动点 2 — 失败时给提示**（`tools.py` 的 `run_python()`，输出截断之后追加）：

- 若输出里出现 `FileNotFoundError` 或 `No such file or directory`，
  追加一句「cwd 是 `sandbox/`，请改用 `DATA_DIR + '/xxx.csv'`」。
- **为什么必须要这一条**：`_guard` 只拦「项目外路径」，而**相对路径根本不触发 `_guard`**，
  所以工具原来的那句「请改用 DATA_DIR」提示**在真实的失败场景里从来没出现过**。
  模型看到的只是一个裸 `FileNotFoundError`。

**验证（两道，都不经模型，可复现 —— 跑法：`& $PY eval\verify_xxx.py`）**：

| 验证 | 脚本 | 结果 |
|---|---|---|
| 路径能力 | `eval/verify_sandbox_path.py` | **6/6 通过**：相对路径 → `FileNotFoundError`；`DATA_DIR+'/hard/products.csv'` → 8 行；**`DATA_DIR` 跨文件 join → 270 行，电脑 4842055（与正确答案一致）**；反例（不 strip 产品名）→ 4485258（错值，正好差 356797）；项目外路径 → 仍被拦；`cwd` → `sandbox/` |
| 修复生效 | `eval/verify_fix.py` | **6/6 通过**：新描述里 `DATA_DIR`/`sandbox` 都在；失败时提示确实追加；**成功时不误报**提示；`DATA_DIR` 读文件读到 240 行；项目外路径仍被拦 |

> 脚本本身也踩过坑（第一版 join 那条"只检查没报错"⇒ 错了也打 ✅），
> 已改成必须断言输出里的具体数字。详见文末**附录 B**。

**端到端效果**：`hard` 集 **6/12 → 11/12**，`run_python` 链路 **0/5 → 8/9**。

**方案 B 为什么不做**：把 `cwd` 改成 `BASE_DIR` 会让被执行的代码可以往**项目根目录**写文件，
安全姿态被实质放宽；而方案 A 已经拿到同样的效果 —— 不值得为省一个 `DATA_DIR` 前缀去换隔离性。

## 缺陷 2【★★ 严重】跑到最大步数时，DSML 泄漏检查被绕过

**位置**：`main.py` → `run_agent()` 末尾的兜底分支

```python
# 到了最大步数还没给出最终回答 → 最后再问一次
final = client.chat.completions.create(model="deepseek-chat", messages=messages)
return {"answer": final.choices[0].message.content, ...}   # ← 没有 _looks_like_tool_markup 检查
```

DSML 检查（`_looks_like_tool_markup` + 重新生成）**只在 `if not msg.tool_calls` 那条正常路径上做了**，
兜底分支直接返回原文。

**证据**：修复前，H03、H07、H10、H11 的最终回答**全部**带着 `<｜｜DSML｜｜>` 标记。
典型的一条（H07 的最终回答，直接交给用户的原文）：
```
The sandbox working directory differs from the project root. Let me locate the actual project path.

<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="run_python">
<｜｜DSML｜｜ parameter name="code" string="true">import os, glob
...
```

**修复后仍然存在**：`hard_v2` 里唯一失败的就是 H12，失败原因正是这个 ——
它的回答以 `The 数量/单价 columns contain non-numeric text. Let me coerce types. <｜｜DSML｜｜ calls> ...` 结尾。
**即：这个缺陷没有被缺陷 1 的修复顺带解决**（两者位置不同：一个在工具描述，一个在 `main.py` 兜底分支）。

**影响**：**恰好是最需要兜底的场景**（模型已经卡住 5 轮）反而输出了最不该出现的东西 —— 用户看到一堆内部标记。

**修复建议**：把兜底分支也过一遍 `_looks_like_tool_markup`，命中就再要求一次"只用自然语言重述"；
或者干脆在兜底时**不再让模型自由生成**，改成直接返回一个结构化说明（"已达最大步数，以下是已获得的信息：…"）。

## 缺陷 3【★ 中等】`describe_csv` 会**掩盖**脏数据

**位置**：`tools.py` → `describe_csv()`

```python
nums = pd.to_numeric(s, errors="coerce")
if nums.notna().sum() >= max(1, len(s) // 2):
    lines.append(f"  - {col}（数值列，缺失 {miss}）：min={nums.min():g} max={nums.max():g} mean={nums.mean():.2f}")
```

它用 `to_numeric(errors="coerce")` **清洗之后**再报 min/max/mean，
于是当 `单价` 实际是 `object`（混着 `"2,599"`）时，输出却是：

```
- 单价（数值列，缺失 12）：min=149 max=5899 mean=...
```

`df['单价'].dtype` 实际是 **object**，但描述里说它是"数值列"。

**影响**：模型据此以为该列可以直接算，于是用 `aggregate_csv(value_expr="数量*单价")` 或直接相乘 → 报错。
（H12 的回答里就出现了 `can't multiply sequence` 这类错误。）

**修复建议**：把"原始 dtype"和"可清洗成数值"两件事分开说，例如：
```
- 单价（**文本列**，缺失 12；其中 15 个值含千分位逗号，可直接转数值）
```
这样模型一眼就知道要先清洗。

## 缺陷 4【轻微】`aggregate_csv` 的 `top_n` 被静默截断

**位置**：`tools.py` → `aggregate_csv()`，`top_n = max(1, min(int(top_n), 50))`

**证据**（H03 轨迹）：模型传 `top_n=270`，返回"前 **50** 名"。
虽然返回文案里写了"前 50 名"，但**没说明"你请求的 270 被截断了"**，
模型可能误以为拿到了全部分组。

**修复建议**：当 `top_n > 50` 时在返回里加一句
「（你请求 270 名，超过上限 50，已截断）」。

## 这些问题为什么值得写进简历

1. **主评测集跑不出来，只有脏数据难度探针能跑出来** —— 说明"评测集设计得够不够狠"直接决定能不能发现问题。
2. **失败不是零散的，而是集中在一整条链路上（`run_python` 0/5）** —— 这比"50% 完成率"这个数字有用得多。
3. **缺陷 1 是接口不一致**（工具的 cwd 与项目的路径约定），**缺陷 2 是防御逻辑漏了一条分支**，
   **缺陷 3 是工具描述与真实行为不符** —— 三类都是"看起来没问题、跑起来才暴露"的工程缺陷。
4. 每一条都有**可复现的证据**（原始轨迹与分析脚本都在 `eval/` 下）。
5. **修复有归因、不是"重跑一次运气好了"**：修复只动了工具描述和失败提示，
   而提升的 5 条**全部**是修复前卡在 `run_python` 上的题；沙箱、`cwd`、判分规则都没动。

## 附录：我自己犯的一个错（标准答案算错了，比模型还错）

这是本次最值得记下来的教训，**不是模型的缺陷，是我的**。

**错误**：第一版 `eval/gen_hard_set.py` 里用
```python
price = pd.to_numeric(df["单价"], errors="coerce")   # ← 错在这里
```
算「销售额 = 数量 × 单价」。而脏数据里 **15 个单价是 `"2,599"` 这种带千分位逗号的文本**，
`pd.to_numeric("2,599")` **不报错，直接静默返回 `NaN`**（因为我没有先去掉逗号）。

**后果**：15 行单价被当成缺失丢掉 → 所有销售额口径的答案**系统性偏低**，例如：

| 题目 | 我的标准答案（错） | 模型回答（对） | 真实值（现在） |
|---|---|---|---|
| H10 手机销售额 | 2515371 | **2755311** | 2755311 |
| H11 外设销售额 | 1212562 | **1246336** | 1246336 |
| H12 最高类别 | 算错 | **电脑 4842055** | 电脑 4842055 |

**更严重的是第二层错误**：我发现分数不对后，写了个"复核脚本"去验证 ——
但**复核脚本里复用了同一个错误表达式**，于是它"验证"出了同一个错误值，
我差点就把这个错误结论当成"模型答错了"写进报告。
**用同一个有 bug 的表达式去验证，只会确认错误。**

**修法**：先 `.str.replace(",", "", regex=False)` 去掉千分位，再 `to_numeric`。

**关键对照**：重新生成脏数据 CSV 后，`Get-FileHash` 与修复前**完全一致** ——
即**改的只是标准答案，一个字节的数据都没动**。这一点很重要：
如果数据也变了，那"6/12 → 11/12"的提升就没法归因了。

### 附录 B：我在"验证"这件事上又犯了一个错（一个不会失败的检查）

写 `eval/verify_sandbox_path.py` 的第一版时，我把 join 那条写成：

```python
good = (got_ok == expect_ok)      # got_ok = "没抛异常"
```

于是脚本打印出 `[OK] ★ 跨文件 JOIN ... 实际 -> 270 行 / 电脑 4485258` ——
**✅ 通过了，但数字是错的**（正确是 `4842055`）。
它只检查了"没报错"，没检查"算出来对不对"，所以**这个检查永远不会失败**。

错在哪：我漏了 **`str.strip()`**。脏数据里有 14 行产品名首尾带空格，
直接 `merge(products.csv, on="产品")` 这几行**匹配不上**，销售额就少了 **356797**。

**修法**：给每条用例加一个 `must_contain`（输出里必须出现指定串）的硬校验，
并把 `(3b)` 那条错误写法**也留成一条用例**（期望 `电脑 4485258`）——
这样以后谁改代码，"正确做法"和"错误做法"的差异都会被当场断言出来。

> **教训（两次是同一类错）**：
> 附录 A 是"用同一个 bug 去验证 bug"，附录 B 是"用不会失败的断言去验证"。
> 两者都会给出**绿色的假信号**。
> 验证的价值不在于"我跑了一个脚本"，而在于**这个脚本有能力失败**。

### 附录 C：一个容易误读的口径差异（不影响判分，但别混用）

`hard_set.json` 的 `meta.injected_dirt` 写着「产品名首尾空格：**12**」，
但最终文件里带空格的行是 **14** 行。两个数都对，**口径不同**：

| 数字 | 含义 |
|---|---|
| **12** | **注入时改动**的行数（`N_SPACE_PROD = 12`） |
| **14** | **文件现状**：注入空格后才复制 10 行重复行，其中 2 行原本就带空格 → 12 + 2 = 14 |

所以"不 strip 会少 **356797**"这个差额对应的是 **14 行**。
同类情况还有「数量缺失：10 行」（注入 8 行 + 2 行重复副本 = 10 行）。
